# Remediation batch B6: notification delivery

Base: `claude/integration-defects-20261020` @ `0496b14` (B0–B5, F1, F2, F4). Evidence: `docs/operational-audit-20261020/reconciliation-20261020/R4-training-notifications.md` (TRN-01/05/08/10/13/16/19/35) and plan README §5 (B6).

**Owner constraint:** "You may prepare and test the notification scheduler implementation locally, but infrastructure changes require a separate proposal and authorization."

This batch therefore changes **application code, tests and one new AWS migration (047)**. It does not change `infra/**`, `.github/workflows`, release configuration or the provider-reachability gate, and nothing was deployed. The invoker (a scheduled caller of the two job routes) exists only as a proposal: [`B6-infrastructure-proposal.md`](B6-infrastructure-proposal.md).

**Until that proposal is authorized and deployed, TRN-08 and TRN-01 are fixed in code but nothing calls the job routes in AWS.**

## Defects addressed

| ID | Defect | Change |
|---|---|---|
| TRN-08 (Critical) | In aws-native mode, the request proxy answered 401 to a bearer-secret-only call before `POST /api/notifications/email-dispatch` could run. The route also compared the secret with `!==`, which is not constant-time. | `request-proxy-core.ts` lets through exactly two paths, `/api/notifications/email-dispatch` and the new `/api/notifications/generate`. These paths have no session; each route verifies the secret itself. Every other path keeps its session requirement, including `/api/notifications`, `/api/notifications/preferences`, sub-paths of the two job routes and `/api/internal/*`. Both routes now use `authorizedNotificationJob` (`src/lib/notifications/job-authorization.ts`): `timingSafeEqual` over SHA-256 digests of the header and `Bearer <secret>`. It accepts the same secret as before (`NOTIFICATION_DISPATCH_SECRET`, else `CRON_SECRET`) and fails closed when neither is set. **No scheduled invoker was added; see the proposal.** |
| TRN-01 / FLT-05 (Critical) | Alerts and their emails were generated only inside `GET /api/notifications`, and only for the user making the request. Members who never opened the web app got no alerts, and the mobile inbox only reads rows. | New `POST /api/notifications/generate`, protected by the secret and **AWS-native only** (otherwise 503). It runs the **existing** per-user generator for every active member of every active agency. The generator was moved unchanged from `route.ts` into `src/lib/notifications/user-notification-generator.ts`, and `GET` now calls the same `reconcileUserNotifications`. Source reads that need a session are injected: `GET` passes its cookie-forwarding `internalJson`; the scheduled run passes a reader that reports those sources unavailable. Each member is generated **in that member's own subject-bound session** (`resolvePostgresAccess` as that user, so the same permissions, features, RLS and `TenantBoundNotificationEventWriter` apply, and email goes through the 024 enqueue function). A member is skipped if the access resolver does not return exactly the listed agency. Details: (1) members are listed by `tracepoint_auth.list_notification_generation_targets` (047: runtime login only, active membership in an active agency, ordered, at most 500 rows); (2) each call handles one page (`limit`, default 50, max 200) and returns `nextCursor`; (3) an optional `departmentId` limits the run to one agency; (4) a session advisory lock on a dedicated connection gives a concurrent run **409**; (5) idempotency comes from the existing event and queue upserts and the fingerprints; (6) a member's failure is counted and logged (`notification_generation_member_failed`, ids only), the run continues and returns **503**. No new alert rules and no new routing. Sources computed: **Training** (certification readiness and agency training) and **Fleet**. Personal Rifle, Ammunition, Inspection, Range, Qualifications and (when the feature is on) Equipment are read only through session-bound internal routes. The scheduled run does not generate them and, because they are "unavailable", does not resolve their existing rows. |
| (found in B6) AWS-native DATE values | The real-PostgreSQL run showed that the AWS-native `pg` driver returns `date` columns as JS `Date` objects. The certification evaluator expects provider text (`YYYY-MM-DD`), so **every certification with an expiration date evaluated as "expired"** with "Certification requires an expiration date, but no valid expiration can be determined." This affects `GET` today, and enabling the scheduler would email this false Critical alert to every member. | The generator's certification mapping normalises `Date` values to calendar text (`calendarDate`, using local components because the driver builds local-midnight dates). This is a narrow fix on the B6 path only. **The global contract question is NOT fixed and needs an owner decision** (see below). |
| TRN-10 (Medium) | The fingerprint was `JSON.stringify(item)`, which includes daily-changing detail text ("expired 10 days ago"). Each day it reset snoozes and acknowledgements and queued a new email. | `notificationFingerprint` is now `{v:2, key, source, kind, title, priority, createdAt}`: one value per alert condition (the entity key, kind and severity, and the condition date). Detail text no longer counts. A changed kind, severity or condition date still reopens the alert. Snooze and acknowledge semantics are unchanged. **Upgrade path:** a stored pre-v2 fingerprint is compared by condition. If the condition is the same, the stored fingerprint is **kept**, so the dispatcher still matches the queued row, and the deploy itself neither resets snoozes nor re-sends email. |
| TRN-13 (Medium) | My Home hid Acknowledge for 9 kinds; the API refuses 21 kinds with 409. | One list, `src/lib/notifications/acknowledge-policy.ts`. `PATCH /api/notifications` uses it for the 409, and My Home uses `notificationCanBeAcknowledged(item.kind)`. `/notifications` had the same defect (Acknowledge on every open item) and now uses the same rule. Snooze is unchanged. |
| TRN-16 (Low) | The dispatcher sent already-queued digests to members deactivated after queueing. | Before sending, each recipient group is checked. AWS-native calls `tracepoint_auth.notification_recipient_active` (047: runtime login only; active membership in an active agency). Bridge reads `department_memberships` through its existing service-role client (`src/lib/notifications/dispatch-recipient.ts`). Inactive groups are marked `Cancelled` with "Recipient is no longer an active member." and counted in `cancelledItems`. A failed lookup retries, like an event-lookup failure. |
| TRN-19 (silent-failure part only) | Off-duty re-notification upserts had no `onConflict`. The AWS-native client defaults to `id`, so a second notification for the same key failed with 23505, which `console.error` swallowed. | The three upserts (request submit, resubmit, officer decision) pass `onConflict: "department_id,user_id,notification_key"`. They also reset `acknowledged_at`/`snoozed_until`, so the reopened event is visible. **Not changed:** off-duty email routing, which is a feature decision. **New finding (not fixed):** in AWS-native mode, these writes create rows for **other** users (reviewers, the requesting officer). The `notification_events_own_rows` RLS policy rejects them with 42501, whatever the conflict target. In AWS-native, off-duty notifications to others therefore still fail, and silently. The fix needs a server-only cross-user write path, like 024; that is an owner decision. |
| TRN-35 (Low) | `in_app_enabled=false` made the generator produce nothing, so it queued no email and resolved every open alert. | Fixed. The UI cannot set false, so only legacy rows hold it. The generator no longer reads the flag, and `getPreferences` reports `true`. The `/notifications` page still shows an "In-app notifications" checkbox that cannot be saved as off, as before; removing it is a UI decision. |
| TRN-05 | Due-soon items are not emailed by default (`critical_email_only` defaults to true). | **Not changed:** owner decision pending. The generation run applies the same preferences. |

## Owner decisions and findings

1. **Authorize the infrastructure proposal** (`B6-infrastructure-proposal.md`). Without it, nothing calls either route in AWS.
2. **AWS-native DATE contract (new, cross-cutting):** `date` columns arrive as `Date` objects everywhere on AWS-native. Supabase returns `YYYY-MM-DD`. B6 normalises only the certification-readiness input. Other readers that build `${value}T00:00:00Z` or display the value (for example fleet alert detail "Configured date: Thu Oct 01 2026 …", the `/training/certifications` API, qualification history) may be wrong. Two fixes are possible. (a) A global `date` (OID 1082) text parser in `postgres-type-parsers.ts`, next to the existing int8/numeric provider-contract parsers: one line, but it changes JSON for `/api/mobile/*` from ISO timestamps to `YYYY-MM-DD`, so the mobile client must be checked. (b) Per-reader fixes. Recommend a dedicated batch.
3. **Off-duty notifications for other users are RLS-denied on AWS-native** (TRN-19 follow-up). This needs a server-only enqueue-style function for cross-user events, plus the routing decision.
4. **TRN-05** (due-soon email default) is unchanged and still pending.
5. **Supervisor and staff routing of scheduled alerts** is deferred as an enhancement, as instructed. The generator still keeps only the member's own readiness rows. Agency-training `_staff` alerts still go to staff members, through the existing rule, because each staff member is generated as themselves.
6. Sources that need a session (Personal Rifle, Ammunition, Inspection, Range, Qualifications, Equipment readiness) are **not** generated by the scheduled run. Covering them needs those route handlers refactored into session-free readers, as a separate change.
7. The scheduled run uses the **same secret** as the dispatcher, the existing `NOTIFICATION_DISPATCH_SECRET`. A member without a profile email fails generation, counted and logged. In AWS-native mode `GET` behaves the same way when the Cognito email is empty; 024 already requires the profile email.

## Rollback

- Application: revert the commit. `GET /api/notifications` returns to its previous self-contained form. v2 fingerprints already stored stay valid strings: after a revert they look "changed" once, which gives one reset or email per open item, the same as one day of the old behaviour.
- Infrastructure: disable or delete the schedules (proposal §8). The routes do nothing unless called.
- Schema: the ledger is hash-checked, so roll back with a new forward migration:

  ```sql
  begin;
  drop function if exists tracepoint_auth.list_notification_generation_targets(uuid, uuid, uuid, integer);
  drop function if exists tracepoint_auth.notification_recipient_active(uuid, uuid);
  commit;
  ```

  Only do this after reverting the application: the dispatcher's AWS-native recipient check calls `notification_recipient_active`, and a missing function makes each group retry, not send.
