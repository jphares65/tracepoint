## Notes

**Merges (same root cause)**
- **C-63 + C-01 (+ C-64):** these are one custody-workflow gap. The Focus drawer sends users to the record page, whose only custody actions call a superseded API contract. The Restricted tab on `/firearms` is the one working path, and it drops notes (C-64). Fix C-63 by deleting the form or pointing it at the Restricted tab, then fix the C-01 copy and link in the same change.
- **C-04 + C-05:** C-05's fix (land on the saved record) depends on C-04 (history list).
- **C-03 + C-06 + C-07:** these share one root: the inspection form does not reflect B8's status effects. Prefilled Passed, stale copy and an unguarded Save combine so that one accidental click can produce a duplicate Passed inspection that also returns a failed firearm to service.
- **C-08 + C-23:** both come from the magazine count inputs. One component fixes both: string state, required, no prefill.
- **C-02 + C-11:** both are status-normalisation problems in the inventory counts. Fix them in the same `normalizeStatus`/`inventoryCounts` change.

**Newly noticed while verifying**
- **C-R1 (S3, NEW-UNASSIGNED, PROD/STG/RC Present):** Reconciliation "Save Draft" after submission silently reverts a Submitted reconciliation to Draft (`api/armory/ammunition/reconciliations/route.ts:497-498`; button `reconciliation/page.tsx:427-438`). It is recorded under C-38 but is a functional status regression in its own right, so it could be tracked separately. **Update 2026-10-22:** fixed in the release candidate. Save Draft and a second Submit are refused on a Submitted record, and Withdraw is an explicit action that needs a reason and writes an audit record atomically. The owner's requirement for a dedicated withdrawal permission is open as **R-WD-1** ([remediation-plan.md §11](../remediation-plan.md#11-open-requirements-carried-forward-do-not-drop)).
- **C-R2 (S3, NEW-UNASSIGNED, STG/RC Present, PROD Absent):** the record-page custody buttons are gated by `firearm_custody.check_in/check_out/override` or `manage_firearms` (`api/armory/firearms/route.ts:73-84`). The live RPC (031) authorises only the assignee or `manage_restricted_firearm_custody`, and only under an active `duty_only` restriction. Even if C-63's body were fixed, users with the wrong permissions and firearms with no restriction would still see the buttons and get 42501→403 or 409. The C-63 fix must also re-gate the buttons.
- The record page's "Custody History" (`[firearmId]/page.tsx:596`) shows `event.reason`. New events from 031 store `reason = 'CHECK_IN'/'CHECK_OUT'` and the user's text in `notes`, which is not shown. Display only (S4); fold it into the C-63 fix.

**Where the "likely production" inference matters**
- **C-63 / C-R2:** if PROD really is @564ff78, production has neither the transfer form nor the new API, so the defect is live only in staging. Releasing the RC as-is would ship a custody form that always fails into production for the first time. That is why it is rated S2 but should be fixed before release. If production actually runs something at or after 2c7bc51 (e.g. the staging build), the defect is already live there.
- **C-03:** the RC-worsened part (Passed → In Service) reaches production only with the RC. The zero-touch Passed default is already likely in production.
- **C-59:** likely production has no QR resolve endpoint at all, so B5 is a net-new capability there.
